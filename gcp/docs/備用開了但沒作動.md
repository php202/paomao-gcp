# 「備用有開，但沒有作動」— 兩種情況與對應處理

---

## 情況一：LINE 輸入「我要打卡」→ 備用（config 備援）有開，但機器沒回覆

**可能原因：**

- **Config 備援有生效**：getCoreConfig 從 Script Properties 讀到備援，所以腳本沒在取 config 時掛掉，有跑到「建立打卡連結」。
- **但「回覆訊息」也要 1 次 urlfetch**：`reply()` 會打 LINE API（`UrlFetchApp.fetch('https://api.line.me/v2/bot/message/reply', ...)`），每回一則訊息 = 1 次 urlfetch。
- 若當天 **urlfetch 額度已經用盡**，回覆就會失敗 → 使用者收不到打卡按鈕，看起來就是「沒作動」。

**你要做的：**

1. **確認有設 Script Properties 備援**（`CoreApi_getCoreConfig_backup`）  
   → 至少 getCoreConfig 不耗 1 次，額度留給「回覆」用。
2. **當天若額度已 0**  
   → 無法再從 GAS 回覆任何訊息，需等 **隔日額度重置** 再測。
3. **長期減壓**  
   → 打卡頁接上 **GCP 備援**（`public/checkin-embed-odoo.html`），bind/check_in 改打 GCP，少打 GAS doPost，額度才不會很快用完。

**結論：**  
在 GAS 裡「要回覆就一定要打 LINE API = 1 次 urlfetch」，額度用盡時無法避免回覆失敗。只能靠備援省掉 getCoreConfig 的 1 次、並減少其他 doPost（例如打卡改走 GCP）。

## 情況二：打卡頁「備用」= 改打 GCP，但沒有作動

**可能原因：**

- 前端已偵測 GAS 失敗，改打 **GCP**（`postCheckin` 備援有啟動）。
- 但 GCP 回傳錯誤、或試算表權限不足、或前端沒正確處理回傳 → 畫面上沒成功、沒跳轉或沒提示，感覺「沒作動」。

**你要做的：**

1. **試算表權限**  
   確認 **LINE_STAFF_SS_ID** 試算表已共用給  
   **paomao-967@gen-lang-client-0828139766.iam.gserviceaccount.com**（**編輯者**）。
2. **直接測 GCP 端點**（不經前端）  
   ```bash
   curl -s -X POST https://pao-checkin-api-254258679209.asia-east1.run.app/checkin \
     -H "Content-Type: application/json" \
     -d '{"action":"bind","uuid":"test123","frontUuid":"front456"}'
   ```  
   - 若回 `{"status":"failed","text":"無效的連結 (找不到 UUID)"}` → API 有通，只是沒有這筆 UUID。  
   - 若回 `試算表權限不足` → 照上面檢查共用對象與權限。
3. **看 GCP 記錄**  
   Cloud Run → pao-checkin-api → 記錄，看是否有 500 或權限錯誤。
4. **前端**  
   確認打卡頁有接 **`postCheckin(body)`**，且成功時有依 `data.status` / `data.text` 更新畫面或導向。

**結論：**  
「備用」= 改打 GCP 時，若沒作動，多半是 GCP 權限或回傳內容；照上面權限 + curl + Logs 檢查即可。

## 總結

| 情境 | 「備用」是什麼 | 「沒作動」可能原因 | 你要做什麼 |
|------|----------------|--------------------|------------|
| LINE「我要打卡」 | Config 從 Properties 讀 | 回覆訊息也要 urlfetch，額度 0 就失敗 | 設好備援、等隔日重置；長期讓打卡走 GCP |
| 打卡頁 bind/check_in | 前端改打 GCP | GCP 權限或回傳錯誤、前端沒處理 | 試算表共用給 paomao-967、curl 測 GCP、看 Logs |
